# DB Panel Designer — project notes for Claude Code

Internal tool for electrical design in three steps — **floor plan → wiring → panel** — covering **room layouts** (switches, sockets, lights, fans, industrial gear) with a 3D preview and the **distribution board** they run from. Built for STELCO Malé Power Generation work, used mostly on a phone.

`appMode` is the step on screen: `'plan'` (js/plan.js) · `'wiring'` (js/room.js — called `'room'` before 2.14, and still named room* throughout that file) · `'panel'` (js/panel.js). Body classes `m-plan` / `m-wiring` drive which canvas shows; `body.wiring` is the panel's own wire mode, a different thing.

## Run / build / deploy
- No build step needed for development. Open `index.html` via a local server: `npm run serve` → http://localhost:5173
  (Opening `index.html` directly with `file://` also works on desktop.)
- `npm run build` → `dist/panel-designer-standalone.html` = everything inlined in one file (for testing on a phone from the file manager).
- Deploy: **Cloudflare Workers Static Assets**, git-connected to `github.com/nafaah14/DB-Panel-Designer` — every push to `main` is built (`npx wrangler deploy`) and published; live at https://db-panel-designer.a-nafaah.workers.dev. `wrangler.jsonc` serves the repo root as the site and (2.13) also names the API Worker (`worker/index.js`, which only ever sees `/api/*`) with its Durable Object binding and migration; `.assetsignore` lists what is *not* uploaded (above all `node_modules` — wrangler installs itself there during the deploy and its 129 MiB binary breaks the 25 MiB per-asset limit — and `worker/` + `tools/`, so the API source isn't downloadable). `npx wrangler deploy --dry-run --outdir <dir>` validates the bundle and bindings locally without uploading; with `WRANGLER_LOG=debug` it also lists every `Ignoring asset:` line (its "Read N files" count includes ignored paths and directories). Netlify is no longer used.
- `npm run serve` has no API, so the app runs as a guest there and the cloud UI stays hidden. To work on accounts/sync run `wrangler dev` — see "Accounts & cloud sync → Testing locally".
- Every release gets a semantic version. Run `node tools/bump.mjs <x.y.z> "note" "note"` — it sets `APP_VERSION` (`js/panel.js`), `package.json`, `manifest.webmanifest` and the README title in one go, writes `version.json` (the notes shown under *What's new*), and rebuilds `dist/`. It refuses to write anything unless every file matched. Then add the README changelog line and commit `dist/` with the rest. **Push order matters for the update check:** the site only announces `version.json`'s version once it is deployed, so a release is live when `/version.json` on the live site shows it.

Scripts are classic `<script>` tags sharing one global scope (top-level `const`/`let` are visible across files, so a duplicate top-level name in two files throws — but they are **not** properties of `window`, so from DevTools or an iframe reach them with `win.eval('name')`). `cat` the files together and `node --check` the result to catch a clash before loading the app. Load order: three → panel → room → plan → update → settings → cloud → cloud-sync → cloud-ui → cloud-hist. Boot runs on `DOMContentLoaded` (end of `panel.js`) so everything is defined first. `panel.js` calls into the cloud files (`cloudChanged`, `cloudRowBadge`, …) only from event handlers and boot, never at load time, so the order above is safe — keep it that way.

## Data model (localStorage)
- `pdes.projects.v1` → `{ [projectId]: { name, updated, appVersion, data } }`, `pdes.current`, `pdes.settings` (`mode, scheme, snap, labels, wireColor, wireSize, autoUpdate, plDims, plPts, plRuns`), `pdes.upd` (last update-check result + which version's banner was dismissed); cloud (2.13): `pdes.cloud.session`, `pdes.cloud.meta`, `pdes.cloud.welcome`, `pdes.cloud.seed` — see "Accounts & cloud sync"
- `data = { panels, panelId, rooms, roomId }` — `migrate()` in panel.js upgrades older projects; `normRoom()` in room.js fills room defaults, including `plan` (2.14: `{x,z,rot}` or `null` = not placed yet).
- **`S.items` / `S.wires` / `S.layers` / `S.defs` are accessors onto the current panel**, installed by `bindPanelViews()`. They are not copies: seven places reassign them outright (`S.wires=S.wires.filter(…)`), and a setter is what makes those writes land in the right panel. Reassign `S.panels` itself when replacing the list (see `restore()`), never the views.
- Undo/redo snapshots the whole `data` JSON (`pushUndo()` before a change, then `commit()` / `roomCommit()`).

### Panel designer (js/panel.js)
- Scale **2 px = 1 mm**; 1 DIN module = 18 mm = 36 px (`M`), half-module unit `U` = 18 px.
- `DEFS` = component definitions (`units`, `size`, `terms`, `draw`, `props`, `desc`, `z` draw order). `PANEL_LIB` = library tabs.
- Rail devices store `rail` + `slot` (half-module units). Rails placed end-to-end auto-join (`railJoinTarget`/`joinRails`).
- Wires: `{a:'itemId:termId', b, color, size, layer, path?}`. Auto-routing = orthogonal A* around device boxes (`astar`, `computeRoutes`), lane-spreading via the occupancy map. `path` = manual inner points.
- Layers: `S.layers` (visible/locked/order), items and wires carry `layer`.

### Room designer (js/room.js)
- Units **mm**. Origin = floor corner where Wall D meets Wall A; x along A (width `w`), z along B (length `l`), y up (`h`).
- Walls seen from inside run left→right: A (0,0,0)→(W,0,0), B (W,0,0)→(W,0,L), C (W,0,L)→(0,0,L), D (0,0,L)→(0,0,0). See `wallGeo()`.
- Item `{id,type,surf,x,y,props}`: wall → `x` = centre from wall's left end, `y` = centre height; ceiling → `x` from Wall D, `y` from Wall A.
- `RDEFS` = item definitions (`w`,`h` mm, `depth`, `mount` default height, `model` for 3D, `draw` SVG in mm). `ROOM_LIB` = library tabs.
- 2D editor: `draw2D()`, gestures on `#r2d`, snapping in `snapPos()`.
- **Snapping (2.15).** The magnets and the free-position step are measured **on screen**, not in millimetres — `snapGrid()` gives a ~14 px reach and a step of 50 → 10 → 1 mm as the zoom rises — so zooming in gives real precision instead of fighting a fixed grid. The candidates are what you actually want next to an existing point: **edges touching** (either side), the same height, in line above/below. A neighbour's *centre* is only offered when the two can't collide at that height; offering it unconditionally is what used to drop one socket on top of another. When they would collide, the beside-magnet is widened to reach the other's centre, so a point can't be left overlapping one. `rsnap` records what won and `draw2D` draws a magenta guide through it while a drag is live. Arrow keys nudge the selection 10 mm (1 mm with Shift) via `roomNudge()`, which coalesces a burst of presses into one undo entry.
- 3D: `build3D()` rebuilds the scene from data; `render3D()` renders on demand (`req3D()`); custom orbit (`orb`) — 1 finger rotate, 2 fingers zoom/pan; walls facing the camera are cut away; wall openings are holes in an extruded shape; item fronts use the 2D SVG as a texture (`itemTexture`). Labels are HTML chips projected each frame.

### Room wiring (js/room.js, v2.1–2.3)
- **Circuits live on the PANEL** (`panel.circuits`), not the room — a circuit is a breaker's outgoing way. A room reads the circuits of the boards its DBs point at (`roomPanels()` → `circuits()`); one owner, so nothing is synced. A point names one in `props.circuit` **by id**, so renaming can't orphan it.
- A `db` item's `props.panel` is the board it *is*. `dbForCircuit()` routes each point to the DB whose panel owns its circuit, so two DBs in a room work.
- Promoting pre-2.1 free-text circuit names happens in `linkLegacyCircuits()` (panel.js), **not** `normRoom()` — normRoom can't tell an id from a name now that circuits are elsewhere, and doing it there minted a junk circuit per point on every load.
- Switches carry `props.controls`: one array of load ids per gang. `RDEFS.ways(props)` gives the gang count (`sw`, `swb`, `fanreg`). Never put `controls` in `RDEFS.defaults` — `Object.assign` copies an array by reference and every switch would share one; `normControls()` builds fresh arrays on create/load/edit.
- Conduit is **constructed, not searched** (`routeBetween`, `perimPath`): drop to `runH()` 150 mm under the ceiling, along the walls the shorter way round turning at corners, then to the far point; ceiling↔wall crossings go via the ceiling edge. panel.js's A* doesn't apply — it is single-plane, and these runs cross surfaces.
- **Topology (2.7, extended 2.11):** `roomRuns()` walks items, not circuits. DB→switch and DB→socket are `kind:'feed'` (red); a control device→its targets is `kind:'switched'` (yellow) from a plate switch or `kind:'load'` (orange) from industrial gear — `legKind()` decides, on the *driver's* type. A load on no driver falls back to a direct feed. `effCircuit()` walks **up** the chain (motor → starter → isolator) so only the top needs a circuit set; an explicit choice always wins, and a visited-set caps a user-made loop.
- **Industrial (2.11).** Two sets govern wiring, and both live next to `switchesFor()`:
  - `SWITCHABLE` — loads something can drive (lights, fans, high bays, battens, floods, bulkheads, emergency/exit, `motor`).
  - `CHAINABLE` — control gear that can itself hang off upstream gear (`iso`, `cont`, `dol`, `sd`, `vfd`, `estop`, `pbs`). Plate switches stay out on purpose: it would put every switch in every other switch's tick-list.
  - `canDrive()` = either; `drivablesIn(self)` is what the Edit form ticks, loads first. Adding an industrial *light* means adding it to `SWITCHABLE` or nothing can switch it.
- Circuits carry `phase` (`'1'`/`'3'`, defaulted in `migratePanel`). It drives the BOM's core count and `phaseWarn()`, which flags any point whose `props.poles` starts with `3` on a single-phase circuit — so **name a 3-phase prop `poles` and give it a `'3P'` option** for the check to see it.
- Industrial symbols are enclosures, not flush plates: `encl()`, `cee()` (IEC 60309 face, blue 2P+E / red 3P+N+E), `rotary()`, `pbtn()`, `tube()`. Sizes are the real envelope of the gear, not a symbol size.
- Run colour encodes the conductor, so selection changes width/opacity, never hue.
- Runs are 3D room points. `runOnSurf()` projects them back for whichever surface is being drawn; `nudge()` lifts them 8 mm off the surface in 3D or they z-fight.
- `roomRuns()` is recomputed on demand (no cache) — if it ever shows up in a profile, that is the thing to memoise.

## Conventions
- Vanilla JS, no framework, no bundler. Keep everything working offline.
- Phone first: touch targets ≥ 34 px, test in a 412×900 touch viewport. Pointer Events everywhere; a new primary pointer resets stale gestures.
- `toast()` for feedback, `openModal()` for forms, `reportError()` shows errors on screen.
- Headless testing: Playwright + Chromium; for 3D launch with `--use-gl=swiftshader --enable-unsafe-swiftshader`.

## Testing gotcha
A **service worker from another localhost project** (Daybook, cache `daybook-shell-v3`) can hijack `localhost:5173` and serve stale JS no matter what the dev server's cache headers say. If a change seems not to take effect, check `navigator.serviceWorker.getRegistrations()` before suspecting anything else — this cost several debugging rounds.

### Floor plan (js/plan.js, 2.14)
- `room.plan = {x,z,rot}` (mm, `rot` ∈ 0/90/180/270) positions the room's **local origin** — the corner where Wall D meets Wall A — on the plan; local x runs along Wall A, local z along Wall B. `null` = not placed yet, which is what rooms from older projects and from the wiring step's "+ Add room" arrive as; `planEnsure()` gives those a spot (in a row, `PLGAP` apart) and is called on every enter/refresh/draw, saving only when it actually wrote.
- Rotations are **whole quarter turns** and the sin/cos table (`PLQ`) holds exact integers, so two rooms snapped together coincide to the millimetre rather than to a rounding error — which is what makes a shared wall possible at all. It also keeps every room's rectangle axis-aligned in plan space (`planInner`/`planOuter`), so snapping is plain coordinate comparison.
- **Shared walls.** `planMoveTo` snaps the gap between two facing inner faces to exactly one wall thickness, so both rooms' wall strips land in the same place and the partition draws as one wall. Flush faces and the room's **own current position** are candidates too — the latter so a neighbour inside the snap distance can't drag a room off its spot before the finger has moved. `planResize` uses the same candidates on the dragged wall's axis (`plEdgeCands` maps them into the room's local frame).
- **Drawn in layers, not room by room**: all floors → all wall strips → all openings cut in paper colour → symbols → points/conduit → labels and dimensions. An opening in a shared wall belongs to one room but has to show from both sides, and a later room's solid strip would paint over an earlier room's door. Paper and floor are the same colour, so a cut reads as a gap from either side and no SVG mask is needed (masks make the PNG export fragile).
- Hit targets are a separate layer after the drawing (`dec` / `hit` / `hnd` in `drawPlan`), because in SVG the **last** element painted is the one a tap lands on: rooms, then openings over them, then the resize handles last — handles sit over their own room, so they must come after it.
- Walls A–D in 2D (`wallLocal`) are the shadow of `wallGeo()` in room.js and must agree with it, or doors swing out of the room. `planItemPt` nudges wall items inside so the marker clears the wall (further for the DB box).
- Gestures: drag a room, drag a wall handle, drag an opening (`planNearestWall` re-homes it on whichever wall is closest, corners included). Both the handle and the opening take out the **grab offset**, or the wall jumps to the finger. Resizing clamps the room's items through `withRoom(r,…clampItem)`.
- Selecting a room in the plan also makes it the current room (`switchRoom`), so *Wire this room →*, ⚙ Room and the Edit forms in room.js all act on what is selected. `roomCommit()` redraws the plan when that is the view on screen.
- The plan's library is `PLAN_LIB` + `planThumb` + `planAdd` — the third branch of `renderTabs()` / `$('#lib')`. Export sizes text from the floor's extent, not the current zoom, and takes only the drawing layer.

### Settings & updates (js/update.js, js/settings.js, 2.12)
- **Update check:** `updCheck()` fetches `version.json` with `cache:'no-store'` (10 s timeout) and resolves `'ok'|'offline'|'unsupported'|'error'`, never throwing. It runs ~2.5 s after boot, on `visibilitychange` (if the last check is >45 min old), on `online`, and every 2 h while visible; `settings.autoUpdate===false` turns the automatic ones off. `file:` → `'unsupported'`.
- State lives in `upd` and `pdes.upd`, so the orange dot on `#bMenu` (the `.fab.dot` class, also used for hidden layers) appears at once, not after the first fetch. The banner `#updbar` is dismissed **per version** (`upd.dismissed`); a newer release shows it again.
- **No service worker, on purpose.** Workers Static Assets sends `max-age=0, must-revalidate`, so a plain `location.reload()` already picks up new files; and a worker registered on `localhost:5173` would outlive this project and answer for every other app that dev server hosts (see "Testing gotcha"). If offline support is ever added, scope it to the production host only.
- Settings applies preferences on `change` (no Save button). `importBackup()` adds projects under **new ids** and never overwrites; the whole-device backup is `{app,kind:'backup',schema:1,projects:[{id,name,updated,appVersion,data}]}` and is recognised by `#fileIn` before the single-project check.
- Storage use counts characters, not bytes (browsers meter `localStorage` in characters, ~5 M).

### Accounts & cloud sync (js/cloud*.js, worker/, 2.13)
**Backend** (`worker/`, config in `wrangler.jsonc`)
- Only `/api/*` runs the Worker (`assets.run_worker_first`); every other request is answered by the assets layer without invoking it. Each account is one **SQLite-backed Durable Object** (`UserStore`, `idFromName(lowercased username)`) with tables `account`, `sessions`, `projects`, `history` — one writer per account, which is what makes the `baseRev` check in `put()` a real conflict check. Chosen over KV (eventually consistent), D1 (database id must be created by hand) and Firestore (no Google project to hand). The deploy applies the `migrations` entry itself; tables are created by `register()` only, so probing an unknown username leaves nothing behind.
- **Auth:** the browser stretches the password (PBKDF2-SHA256, 300 000 rounds, salt `pdes/v1/<lowercased user>`) into a 43-char base64url *auth key*; only that is sent, and the server stores `sha256('pdes-pw1:'+auth)`. Sessions are random 32-byte secrets stored as SHA-256 — 120 days sliding, max 20 per account; bearer token = `user~secret`. Six wrong passwords lock the account (30 s, doubling, capped at 15 min); `#verify` reads, compares and writes with no `await` between so parallel guesses can't dodge the counter. Names `[a-z0-9][a-z0-9._@+-]{2,39}`; the client requires ≥ 8 characters. **No password reset, by design.** Optional `INVITE_CODE` variable gates registration only.
- **API:** `GET /api/ping` → `{app:'pdes',cloud:true,invite,now}`; `POST /api/register|login|logout|password|account/delete`; `GET /api/me`; `GET /api/projects` (includes tombstones); `GET|PUT|DELETE /api/projects/:id`; `GET /api/projects/:id/history[/:rev]`. PUT body `{name,updated,app,baseRev,data,snapshot?}` → `{rev,saved}`; **409** `{conflict:true,rev,…}` when `baseRev` ≠ the stored rev; **413** over ~1.5 MB; 300 projects per account. DELETE needs `?base=<rev>` and leaves a **tombstone** (kept 90 days, purged lazily by `list`). Failures come back as `{error}` with the status.
- **History:** `#snapshot` copies the row being *replaced* into `history`, so the current version is never in it. Ordinary saves snapshot at most once per 10 min; `snapshot:true` (sent when keeping both copies) and delete always do; the newest 40 are kept. Restoring from Recently deleted = read the top history row → write it locally under the old id with its meta and tombstone entries cleared → the next sync sees a local project with no meta against a cloud tombstone, which is `push-over` (writes over the delete).

**Client** — `cloud.js` (state, session, auth, scheduling, status dot, boot) → `cloud-sync.js` (engine) → `cloud-ui.js` (modals) → `cloud-hist.js` (Projects-list badges, History, Recently deleted)
- `localStorage` stays the working store; **the app never waits on the network.** State: `pdes.cloud.session` (`{user,token}`), `pdes.cloud.meta` (`{user, projects:{id:{rev,h}}, tombstones:{id:{rev}}}` = the revision each project last synced at and its content hash then), `pdes.cloud.welcome` (first-run prompt answered), `pdes.cloud.seed` (id of the untouched sample project). Change meta only through the synchronous `cloudMeta(fn)`, never read-modify-write across an `await`.
- `cloudDecide(rec,meta,remote,tomb,sig)` classifies each project (`tomb` = a delete made here that hasn't been sent yet): `forget` (nothing left to do), `delete` (send our delete), `restore` (we deleted it but the cloud changed since — the edit made elsewhere beats the delete), `pull-new`, `push-new`, `drop` (deleted elsewhere and unchanged here — remove locally), `push-over` (deleted elsewhere but changed here — write over the tombstone), `adopt` (same id both sides, never synced here), `same`, `push`, `pull`, `conflict`. `sig` hashes the canonical content (name + data, **not** `updated`), so re-saving unchanged content isn't an edit. `conflict`, `adopt` (same id on both sides, no shared history) and a 409 all end in `cloudKeepBoth`: the remote version is saved locally as "<name> (cloud copy)", the local one is pushed over the original with `snapshot:true`, and `rep.again=true` re-runs the sync so the copy uploads at once (without it the copy waits for the next trigger). Identical content = silent adopt, no copy. `cloudSync()` returns a report `{pulled,pushed,kept,blocked,…,again}` — handy in tests.
- A project saved by a *newer* app version is never pulled or overwritten (`cloudNewer`); per-project failures (too large, newer app) go in `cloud.bad` and show as "can't sync". Network errors, 5xx, 429 and 401 abort the whole cycle (`CloudAbort`) so one dead request doesn't mark every project bad. A 401 on the *current* token → `cloudLost()` (state `lost`, red dot, a toast, Account card offers "Sign in again"); it must never be a silent sign-out. Pulls and drops that would change the project open in the editor wait for `cloudIdle()`.
- Triggers: boot (+1.2 s), visibility, focus, `online`, a 2-min poll, edits (debounce 4 s, max wait 30 s), delete (1.5 s). Backoff 20 s → 10 min; a `navigator.locks` mutex stops two tabs syncing at once. `saveProjects()` and `importBackup()` call `cloudChanged()` — **anything new that writes `LS_P` directly must too.**
- **Pristine-seed rule:** the sample project made on a first visit is never uploaded until the user changes it (`cloudIsSeed`), and is dropped silently once the cloud already holds a project — otherwise every new device would add another demo.
- The cloud UI exists only when `/api/ping` answers `app:'pdes'` — so `file://`, the standalone build, `npm run serve` and plain-`http` LAN pages are guest-only. (`crypto.subtle`, needed for PBKDF2, requires a secure context; `https`, `localhost` and `127.0.0.1` qualify.) Sign out keeps local projects by default; "clear this device" removes `LS_P, LS_C, meta, welcome, seed` after a warning that counts unsynced projects, then reloads.
- Accepted gaps: no sharing between accounts; a stale second tab can overwrite a change another tab pulled; a session lost across a reload looks like a guest apart from the one toast / red dot.

### Rooms (2.6)
- Structural changes — add, duplicate, position, resize — go through plan.js (`planAddRoom`, `planDupRoom`, `planDelRoom`) wherever they are triggered from, so a new room always has a spot on the plan. `cloneRoom()` in room.js is the deep copy both use.
- `S.rooms` = `[room,…]`, `S.roomId` = the one being edited; `RM()` resolves it and is how every read in room.js gets the current room. `withRoom(r,fn)` runs something against another room and restores — used by the BOM, which covers all rooms.
- `migrate()` wraps a pre-2.6 single `doc.room` into the list, so old projects and exported JSON still open.
- Duplicating a room (`cloneRoom`) re-ids everything and remaps `props.controls` onto the copies; forgetting that would leave the copy driving the original's lights. `props.circuit` is **kept as it is** unless the id belongs to a room-level circuit from before 2.10 — circuits live on the panel now and both rooms are fed by the same board. Remapping it unconditionally (the 2.10–2.13 behaviour) cleared every point's circuit, since `cmap` is empty for any modern project.
